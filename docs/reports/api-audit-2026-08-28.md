## 8. What changed since 2026‑08‑26

### 8a. NEW — BE‑12: `GET /admin/users/:id` is now an empty route

The previous report named this the **sole source** of `contentCount` and `emailVerified`, because the list
DTO omits both. It no longer returns either. Field‑by‑field comparison:

```
LIST   DTO keys: createdAt, displayName, email, id, isActive, onboardingCompleted, plan, roles, username
DETAIL DTO keys: createdAt, displayName, email, id, isActive, onboardingCompleted, plan, roles, username

detail adds:  NOTHING          contentCount: undefined     emailVerified: undefined
```

**Consequences today:**

| Impact | Detail |
|---|---|
| Dead column | The creator directory's **Content** column now renders `—` for all 21 rows |
| Two inspector fields vanish | Content and Email‑verified are conditionally rendered, so they silently disappear |
| Wasted round trip | Selecting a creator fires `GET /admin/users/:id` that returns nothing new — ~390 ms per selection for zero information |

**The UI does not lie about it** — the table shows `—` rather than a fabricated `0`, and the inspector omits
the rows entirely. That was deliberate defensive design and it held. But the feature is degraded, and the
detail fetch should either be dropped or the backend should restore the two fields.

## 10. Verification honesty

Not every endpoint can be exercised against production without consequences, so three techniques were used
and each row above is labelled accordingly.

| Tier | Count | What it proves |
|---|---|---|
| **Read** | 22 | a real success response |
| **No‑op write** | 8 | a real 2xx **plus a read‑back confirming state was untouched** — `users/:id/active`, `users/:id/roles`, `users/:id/reset-onboarding`, `plans/:plan`, `coach/categories/:id`, `coach/questions/:id`, `auth/logout` |
| **Probe** | 6 | the route exists and enforces its rules, via a well‑formed nonexistent UUID or an empty body. **Does not prove the success path.** |

**The 6 probe‑tier rows are the honest gap in this audit:** `content/:id/approve`, `content/:id/takedown`,
`coach/categories` (POST), `coach/categories/:id/questions` (POST), `jobs/:id/retry`, and the `limit` cap.
Approve and takedown cannot be fired because live content is only `draft`/`published`/`publishing` — there
is **no `deleted` or `moderation_rejected` row** to act on idempotently. Coach create cannot be fired
because there is still no `DELETE`, so the test row would be permanent. Retry cannot be fired on a genuinely
failed job because it costs real provider spend.

**To close them**, any of: a disposable content id, a staging environment, or a `DELETE` for coach
categories.

Two rows in the first pass of this audit were reported as failures and were **my probe's fault, not the
API's** — corrected here:

| Endpoint | First‑pass error | Cause |
|---|---|---|
| `POST /admin/users/:id/roles` | `400 Action must be 'grant' or 'revoke'` | probe sent `{role}`; the API needs `{role, action}`, which the app already sends |
| `PUT /admin/plans/:plan` | `400 property plan should not exist` | probe echoed the GET body back; the PUT DTO forbids `plan`/`updatedAt`, which the app already strips via `Omit<PlanLimits,'plan'\|'updatedAt'>` |

Both return **200** with the correct body. Neither is a defect, but both are **undocumented asymmetries**:
`GET /admin/plans/:plan` cannot be round‑tripped into `PUT`, and the roles endpoint's `action` field is not
in the spec doc.
